# Approach write-up (1 page)

**What I prioritised.** The brief weights AI integration and architecture highest, so I built the core ticket flow first and treated AI as an enrichment layer: a ticket is committed and acknowledged before any AI work starts, so an AI outage can never block authors or admins. The highest-risk part of AI-drafted support is saying something false about money, dates or book status, so the design leans on deterministic code: PostgreSQL is the source of truth for author facts, the Knowledge Base for policy, and a validator rejects drafts that contradict either.

**How AI is used (and not used).** One structured classification call returns category, priority, confidence and an *intent*. The intent drives a deterministic router (DB-only / KB-only / hybrid / insufficient), so simple factual questions are answered from the database with no LLM at all, policy questions pull a single KB section, and anything the data cannot support goes to a human instead of being guessed. Drafts are cached by a six-part key, never regenerated on refresh, and every call is logged with tokens and latency. Providers (Gemini/OpenAI/Anthropic) sit behind one interface with fallback on retryable failures only. Model choice: a small, low-cost model per vendor, because prompts are short and fully grounded - *(record the deployed models here)*.

**Trade-offs.** In-process job queue and in-memory rate limiting instead of Redis/BullMQ (single instance, durable state lives in Postgres); keyword topic detection for follow-up messages instead of an LLM call per message; category-to-section KB lookup instead of vector search; hand-written UI components instead of a component library; attachments are UI-only. I assumed calendar quarters for the payout schedule.

**Evolving to production.** Durable worker queue and horizontal scaling (shared rate limiting, Socket.IO adapter), real file storage with virus scanning, SLA timers and escalation rules, per-admin workload views, an evaluation set to track classification accuracy and draft acceptance/edit rate from `ai_runs` and sent messages, cost dashboards and budgets per provider, editable Knowledge Base with review workflow, and observability (traces, alerts on fallback rate).
